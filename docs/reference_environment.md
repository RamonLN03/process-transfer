# Reference environment

What this is: one known-good, pinned environment that reconstructs the software used to
generate and check the registered M0 results (M0-E05, M0-E06, M0-E07, M0-E08, and the
suite of 725 tests at this commit). It is a diagnostic and reproduction aid, not the
project's dependency contract, and it is not installed by CI.

## Scope, stated plainly

* **Python 3.13.7, Windows** (the development machine `platform.platform()` reports
  `Windows-11-10.0.26200-SP0`). This is where the registered data sets and the numbers
  quoted in `docs/m0_audit.md` and `docs/experiment_log.md` were produced.
* **Continuous integration is a separate environment on purpose** (`.github/workflows/ci.yml`):
  Ubuntu, Python 3.12 and 3.13, with unpinned current versions of every dependency. CI
  proves the software runs and the suite passes on Linux under both supported Python
  versions; it never runs the experiments, so it says nothing about the registered
  numbers. Validating this reference lock file on Linux or another Python version has
  not been done and is not claimed here.
* This file pins the interpreter **and** every direct and transitive dependency it was
  captured with. `pyproject.toml` keeps its own looser lower bounds, which is what a
  library should state; this lock file is a snapshot for reconstruction, and installing
  it does not change `pyproject.toml`.

## Reconstructing it

Outside any synchronised folder (OneDrive, Dropbox: a venv or an open DuckDB file
inside one is at risk of being touched mid-write, `docs/decisions.md` D-014):

```
python -m venv <path-to-venv>          # Python 3.13.7
<activate the venv>
pip install -r requirements-reference.lock.txt
pip install -e . --no-deps
```

`--no-deps` on the second command matters: installing the package normally would let
pip re-resolve its dependencies against `pyproject.toml`'s looser bounds and could
replace a pinned version. The lock file has already installed every dependency the
package needs; the second command only makes `process_transfer` importable from `src/`.

## Validating it

```
ruff check .
pytest
python experiments/08_oracle_conductance.py
```

The first two are the project's standing checks (`AGENTS.md`, `README.md`) and are
expected to pass exactly as they do in the registered environment: **725 tests**, ruff
clean. `PT_DATA_DIR` should point outside the repository for the third, for the same
synchronisation reason as above; it writes `summary.json` and two figures under
`PT_DATA_DIR/experiments/m0_e08/<run id>` and exits non-zero if any of its three
verdicts (H1 anchoring, H2 numerical resolution, H3 validity) fails.

## Exact reproduction against numerical agreement: two different claims

These are not the same claim, and this file only makes the first one, and only where it
has been tested.

* **Exact content reproduction** (`docs/decisions.md` D-012): a generated data set's
  content hash depends on the code, the configuration, the seed and the numerical
  environment together. `docs/m0_audit.md` already records that this does **not** hold
  across numpy/scipy versions: the six runs of M0-E05 had different content hashes
  under numpy 2.3.5/scipy 1.16.3 than under 2.5.3/1.18.1 on the same machine at the same
  commit. This lock file pins the versions the registered hashes were produced under
  precisely so that exact reproduction is possible again; it has not been tested on a
  machine other than the one that captured it, and no claim is made about hash equality
  on a different OS, CPU architecture, or BLAS backend, tested or not.
* **Numerical agreement across environments** (`docs/decisions.md` D-025): the DuckDB
  version matrix already on record is the model for this weaker and more portable
  claim, that the software's behaviour and the tests it must pass hold across several
  library versions, without the generated bytes being identical. This lock file's
  Python, numpy, scipy, pandas, pyarrow and DuckDB versions are one point already known
  to satisfy the stronger claim (the registered environment itself); nothing here
  extends the DuckDB matrix or repeats it for other libraries.

Do not promise hash equality, or even numerical agreement, on a system or a version
combination this file has not actually been installed and run on.

## What was validated when this file was written

`requirements-reference.lock.txt` was installed into a clean virtual environment
outside this repository and outside any synchronised folder, with the two-step
install above, on the machine that captured it (Python 3.13.7, Windows). `ruff check .`
and `pytest` both passed there (725 tests), and `python experiments/08_oracle_conductance.py`
returned exit code 0 with all three verdicts holding. The isolated environment's
`pip freeze` was compared against `requirements-reference.lock.txt` and differed only in
the absence of the editable local package line, as expected. See
`docs/experiment_log.md` for the run's provenance record.
